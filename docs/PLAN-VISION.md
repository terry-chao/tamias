# 图纸识别（RF-DETR）：实施方案

> 状态：**方案（未开工）**。检测器已定：**RF-DETR**（Apache-2.0 档）。
>
> 一句话：**检测器只回答「哪里有什么」，几何与尺寸仍然来自矢量。检测结果是喂给现有
> `DrawingImportPlan` 的**第二路证据**，不是替换规则识别；人工复核与一步撤销的定位不变。**
>
> **第一次动手直接看 [§8 现在怎么开始](#8-现在怎么开始)。**

## 1. 先划清能力边界

检测器是**栅格图上的二维框检测器**。它能给什么、不能给什么，决定了后面每一个设计：

| 能给 | 不能给 |
|---|---|
| 该区域是门 / 窗 / 柱 / 楼梯 / 电梯 / 洁具 / 家具 | 门的编号（`M0921`）、宽高（900 × 2100） |
| 符号的像素框 + 类别 + 置信度 | 墙的中线、厚度、端点 |
| 区域级标签（剪力墙填充区、楼板开洞） | 图纸比例、单位、标高 |
| 文字块的**位置** | 文字**内容**（那是 OCR 的活，不是检测的活） |

三条推论，后面所有设计都服从它：

1. **墙不出框。** 墙是贯穿整张图的线状结构，框会巨大且互相重叠。墙的几何只能来自矢量；
   视觉最多给「这一片区域是剪力墙填充」这种区域级证据。
2. **尺寸永远不来自检测框。** 框的像素宽高受切片、缩放、线宽影响；尺寸来自矢量实测、
   尺寸/平法标注文字、或默认值 + 警告——和现有 `$INSUNITS` 缺失时的处理同款。
3. **不做「一键翻模」。** 检出结果进**候选表**，人勾选，一条 `ImportDrawingCommand` 撤销。
   [图纸 → BIM](DRAWING-TO-BIM.md) 的「半自动」定位是这条线的**护栏**，不是过渡形态。
   一个看起来很酷但没人敢用的自动翻模，比没有更糟。

## 2. 两类输入，一条管线

现实里的图纸输入分两类，难度和目的都不同：

| | 矢量源（DXF / DWFx / SVG） | 栅格源（PDF / 位图 / 扫描件） |
|---|---|---|
| 几何 | 精确，已有解析器 | 一个像素都没有，全靠恢复 |
| 缺的是 | **语义**（哪几根线是双线墙、填充区是不是剪力墙） | **一切** |
| 比例 | `$INSUNITS` 直接给 | 必须标定（见 §7.2） |
| Ground truth | **有**——规则引擎的输出就是 | 无 |
| 用户占比 | 少（只有你手里的几张） | **多（客户给的基本是 PDF）** |

关键判断：**矢量那类是标定与评测装置，栅格那类才是目的。**

矢量图纸上你能把检测框经精确逆变换投回图纸坐标，逐位比对规则引擎的答案——**这是唯一能
把「检测器对不对」和「比例估得准不准」分离开来测的地方**。先在能精确评测的地方把检测器
调好，再把它指向栅格图纸，那时误差只可能来自标定。

## 3. 管线

```
图纸（矢量 或 栅格）
  → [1] 光栅化，记录变换 T：pixel ↔ drawing          ← 本方案最容易搞反坐标系的地方
    → [2] 切片（1024 px，overlap 192）                ← 不是优化，是必需品
      → [3] RF-DETR 推理（ONNX）
        → [4] 跨片合并（IoU 去重）+ 贴边裁剪
          → [5] 逆变换 T⁻¹ → 图纸坐标的 Detection
            → [6] 空间关联：框内落着哪几根矢量图元
              → [7] VisionEvidence（纯数据，无 Qt、无 engine）
                → build_drawing_import_plan（规则 ⊕ 证据融合，见 §5）
                  → DrawingImportPlan（候选 + 置信度 + **来源**）
                    → 人工复核对话框 → ImportDrawingCommand（一步撤销）
```

第 [7] 步是**加法，不是替换**：`DrawingImportPlan` 的候选本来就带「来源」字段，
视觉候选与规则候选进同一张表、同一套勾选逻辑、同一条撤销路径。

## 4. 类别表（v1，10 类）

| # | 类别 | 形态 | 说明 |
|---|---|---|---|
| 1 | `door` | 框 | 最重要。现在只有图层名或块名能判门，真实 PDF 两样都没有 |
| 2 | `window` | 框 | 同上 |
| 3 | `column` | 框 | 现有矩形柱只有 0.7 置信度（「可能不是柱」），证据可判 |
| 4 | `stair` | 框 | 规则完全没有 |
| 5 | `elevator` | 框 | 规则完全没有 |
| 6 | `sanitary` | 框 | 洁具，规则完全没有 |
| 7 | `furniture` | 框 | 家具，**默认不进模型**（翻模不建家具），但可帮人判断房间用途 |
| 8 | `shear_wall_fill` | **分割** | 剪力墙填充区 |
| 9 | `slab_opening` | **分割** | 楼板开洞轮廓 |
| 10 | `text_block` | 框 | **只定位不识别**，内容交给 OCR（后续） |

两条形态纪律：

- **区域类用分割，不要硬塞进框。** 剪力墙填充区是不规则多边形，外接框会把相邻的墙和门
  一起圈进去。**RF-DETR 的分割版本全档都是 Apache-2.0（含最大的 Seg-2XL），没有许可证
  障碍**——所以第 8、9 类直接上实例分割，不用绕「框 + 连通域」那条路。
- **轴线、墙、梁不要设成类别。** 轴线是贯穿全图的直线，梁要读平法标注文字
  （`KL1(3) 300x600`）。这两样给检测器做都是浪费——见 §1 推论 1。

类别数是**刻意的少**。10 类、每类几百个实例，比 40 类每类 20 个实例训出来的东西可靠得多。
`furniture` 这类「有了更好、没有也行」的，第一版先不标。

## 5. 融合规则：证据怎么用

证据只决定**「看哪里」和「降低多少不确定度」**，不决定**几何形状**。

| 证据 | 现状（纯规则） | 融合后 |
|---|---|---|
| `door` / `window` 框覆盖一簇图元 | 只有图层名或块名才能判门窗，否则**零候选** | 框内图元聚成门窗候选，置信度 0.55；有块名时仍取 1.0，证据降级为交叉验证 |
| `column` 框覆盖闭合轮廓 | 矩形柱 0.7（「可能不是柱」） | 0.95 |
| `shear_wall_fill` 区域覆盖闭合轮廓 | `HATCH` 未支持，填充剪力墙只能靠轮廓猜 | 落在填充区内且闭合 → 0.9，厚度取实测 |
| 框内**没有任何**图元 | — | 丢弃 + 记警告（沿用「宁可不建，也不建到错误的墙上」） |
| 框与框重叠、类别冲突 | — | 高置信度胜；差值 < 0.15 时两条都进候选，标「冲突」，由人裁决 |

三条护栏：

1. **证据不能覆盖几何判决。** 框里检出「门」，但框内的线构不成门窗符号的形状 → 不建候选。
   形状判据仍然在规则侧。
2. **证据不能改尺寸。** 门窗宽度仍取簇的外接框长边（0.4–4.0 m 区间），不取检测框。
3. **默认关闭。** `--vision` / 设置项打开的才走这条路；关掉时纯规则结果**逐位不变**
   （见 §10 回归门槛）。这条纪律与 `TAMIAS_ENABLE_MODULES_MATH`（默认关）、
   RAG「不进内核依赖树」同源。

## 6. 数据：这条线真正的成本

**没有现成的中文建筑图纸标注集。** 数据是最大工作量，也是最容易低估的一项。

### 6.1 自举：从矢量自动标注（先做这个）

```
任何 DXF
  → 规则引擎跑一遍，只取置信度 = 1.0 的候选（有块名的门窗、圆柱、长度达标的墙）
    → 用光栅化时**同一个 T** 把候选的世界坐标投影回像素
      → 得到像素级完美的框标签（COCO JSON）
```

等于把规则引擎已经会的东西**蒸馏到栅格域**。它的价值不在矢量图纸（那里规则本来就跑得动），
而在于——**用户手里 90% 是 PDF 和扫描件，那些图上规则一个像素都用不上，只剩检测器一条路。**

局限必须说清楚，否则会高估它：

- **只覆盖规则引擎已经会的类。** 楼梯 / 电梯 / 洁具 / 索引符号一个都标不出来，必须人工。
- **学到的是规则的模仿。** 规则的错会被一起蒸馏进去，所以只用置信度 1.0 的类，
  且人工抽检 5%（抽检不通过的类退回人工标注）。
- **分布窄。** 线宽、颜色、背景全来自你自己的渲染器。

所以还有一条必做的动作：**验证集必须同时包含「Tamias 自己渲染的图」和「设计院给的真实
PDF」两组**，分开报指标。只用合成集测出来的 mAP 是脚本渲染器上的 mAP，不是产品上的 mAP。

### 6.2 公开集（跨域预训练，可选）

| 数据集 | 内容 | 用途 |
|---|---|---|
| FloorPlanCAD | CAD 图纸 + 符号标注 | 最接近本场景（矢量源）。**许可需自行核实后再用** |
| CubiCasa5K | 北欧住宅平面，分割 | 墙体/房间分割的预训练权重 |
| ArkIndex / Rand Drawing | 法系图纸 | 跨域泛化测试 |

用途是**预训练 + 负样本**，不是直接当训练集——图例、图层约定、符号画法跟国产图纸差得远。
许可一律要先核实，别默认可用。

> RF-DETR 本身带 COCO 预训练权重，这是默认起点。上面这些是「COCO 之外再补一轮」的可选项，
> v1 不必碰。

### 6.3 人工标注

- 工具：**CVAT** 或 **Label Studio**（都开源，都支持框 + 多边形，都能导出 COCO）。
- 冷启动量：**50 张真实 PDF**（至少 3 个不同来源）。
- 工时：一张 A1 平面图约 200 个符号，熟手 30–45 分钟 → **50 张 ≈ 30–40 人时**。
- 分批：先标 `door` / `window` / `column` / `stair` / `elevator` 五类（覆盖价值最高的
  场景），训一版看指标，再决定要不要补剩下的类。

## 7. 工程细节

### 7.1 切片与后处理（必须有，不是优化）

一张 A1（1:100）图纸光栅化后约 **10000 × 7000 px**。直接缩到 640 px 送给检测器，
门宽 900 mm 只剩 **6 个像素**——物理上认不出来。

- 推理：`tile = 1024, overlap = 192`。A1 约需 **90 片**。
- **跨片合并**：RF-DETR 是 DETR，模型内部**没有 NMS**——但这只省掉了图内后处理，
  **跨切片去重仍然要自己写**（IoU 去重即可，不涉及阈值调参）。另外裁掉贴着切片边缘、
  且在邻片没有对应检出的框（切片检测的经典假阳性来源）。
- 训练：**随机裁剪到 1024**，不要整图缩放。
- 类别不平衡：门窗成百上千、电梯楼梯只有几个 → **copy-paste 增广**（把稀有类实例抠出来
  贴到别的图上），简单且对这类目标特别有效。
- 模型规模：Nano / Small / Medium，ONNX 约 10–40 MB。

### 7.2 栅格图纸的比例标定

栅格源没有 `$INSUNITS`。三个办法，按可靠性排：

1. **人工两点定标**（v1 就用这个）：用户在图上点两个已知距离的点（比如轴线间距，
   图上本来就写着尺寸）→ 得到 px → mm。确定、可审计、零算法风险。
2. **图框反推**：A1 = 841 × 594 mm，识别图框四角 → 比例。便宜但受裁切/缩放影响。
3. **尺寸文字 OCR**：读标注文字反解比例。最通用，但要先有 OCR，放到后续。

无论走哪条，**定标结果必须显示给用户确认**，并在误差超阈值时警告——和现有的单位
警告同一个性质：猜错了整个模型尺寸就是错的，而且错得很安静。

### 7.3 双线墙

这是 §1 推论 1 的直接后果，也是把「能看出个形状」变成「尺寸对得上」的关键一步，
且**它不需要检测器**：

```
检测框（或规则候选）给出「这一片是墙」
  → 取垂直于墙走向的扫描线，在框内做一维灰度剖面
    → 找到两条暗带 → 中心线 = 中线，带间距 = 厚度
```

纯 CV、可单测、毫秒级。检测器负责圈出「哪里该扫」，扫描线负责给出「精确到毫米的答案」。

### 7.4 部署形态

| 形态 | 做法 | 取舍 |
|---|---|---|
| **S1 Python sidecar** | `scripts/vision/serve.py`（HTTP）+ 应用侧薄客户端 | 试验期首选：改模型不用重编 C++，零新增 C++ 依赖 |
| **S2 ONNX Runtime 进 C++** | vcpkg 加 `onnxruntime`，`TAMIAS_ENABLE_VISION` 默认 **OFF** | 交付形态：单一可执行文件、不带 Python 运行时 |

两者在 C++ 侧是**同一个接口的两个实现**，切换是构建开关，不是代码分叉：

```cpp
// src/vision/symbol_detector.h（示意）
namespace tamias::vision {

struct Detection {
  std::string cls;
  float score;
  // 图纸坐标，不是像素坐标——T 在模块内消化掉，外面拿到的永远是可用的坐标
  double x0, y0, x1, y1;
  std::string source;   // "sidecar" / "onnx"
};

class SymbolDetector {
 public:
  virtual ~SymbolDetector() = default;
  [[nodiscard]] virtual std::vector<Detection> detect(const RasterImage&) const = 0;
};

}  // namespace tamias::vision
```

`src/vision/` 和 `src/rag/` 同一条纪律：**纯 C++、无 Qt、无 engine、不认识 `Document` /
`Session` / OCCT**。它吃像素、吐检测框。

### 7.5 RF-DETR 的四个坑（写代码前先看）

1. **按名字取输出，不要按形状。** ONNX 图有两个输出：`dets`（`(1, 300, 4)`）和
   `labels`（`(1, 300, num_classes)`）。当 `num_classes == 3` 时，logits 那一维也是 4，
   **和框的最后一维撞上**——按形状匹配会静默把框和类别换过来。
2. **`labels` 是原始 logits，用 sigmoid 解，不是 softmax。** 它是多标签的，
   每个类独立过 sigmoid，不是互斥的类别分布。
3. **框是归一化的 `cxcywh`**（中心点 + 宽高，0–1），要转成 `xyxy` 再乘回像素。
4. **背景槽的位置随权重而变**：官方 COCO 权重没有背景槽，自己训的连续编号权重背景在
   最后一槽。**导出后先用一张已知图对一遍，别猜。**

### 7.6 性能预算

Nano / Small 在 CPU 上跑 90 片：**约 15–60 秒**（CPU 上比 GPU 慢几十倍，要实测）。

→ **必须跑在后台线程，带进度条与取消。** 这与
[AI 接入 §5.2](DECISION-AI-INTEGRATION.md) 的第 9b 条（长调用阻塞 UI）是同一个坑，
不要重犯一次。

> ONNX Runtime 在 CPU 上还有一个已知问题：线程池空转会和预处理抢 CPU。加两行会话配置
> 关掉（`session.intra_op.allow_spinning = 0` / `inter_op` 同理）——只改等待方式，
> 不改计算结果。

## 8. 现在怎么开始

按顺序做，**第 1 步是全方案最关键的一步，而且不需要任何模型**。

### 第 0 步：环境（半天）

```powershell
py -3.10 -m venv .venv-vision
.\.venv-vision\Scripts\Activate.ps1
pip install "rfdetr[train,onnx]"
```

**和 mkdocs 的 `requirements.txt` 分开建环境**，不要装进同一个 venv——
一个是文档工具链，一个是训练工具链，依赖会打架。

### 第 1 步：光栅化 + 验证坐标系（1 天）★ 全方案最关键

`scripts/vision/render_dxf.py`：

1. 读 `assets/samples/drawings/floor-plan-sample.dxf`，画成 PNG。
2. 同时输出变换 `T`（缩放 + 原点偏移）。
3. 把**现有规则引擎的已知答案**画成框叠在图上——这张图的答案是现成的：
   **6 面墙、3 根 Ø600 圆柱、1 樘 900 宽的门（挂在 y = 4000 那道内墙上）**，
   见 [`tests/drawing_import_tests.cpp`](https://github.com/terry-chao/tamias/blob/main/tests/drawing_import_tests.cpp)。
4. **肉眼看框有没有落在墙上。**

框落错了，就是 Y 轴反了或 `world_origin` 没加回去。这个坑
[DRAWING-TO-BIM.md §2](DRAWING-TO-BIM.md) 已经警告过两次，**第三次犯在这里代价最小**。

### 第 2 步：跑通 RF-DETR（半天）

```python
from rfdetr import RFDETRNano
model = RFDETRNano()
detections = model.predict("floor-plan.png")
```

它大概率**认不出门窗**——COCO 那 80 类里根本没有建筑符号。这一步不是要它认对，
是要你看到输出长什么样、把 §7.5 那四个坑对着实际输出核一遍。

### 第 3 步：切片 + 回投（1 天）

把第 1 步的图切成 1024 的块 → 逐块推理 → 跨片去重 → 用 `T⁻¹` 投回图纸坐标。
做完这一步，你可以把任意一张图的检测框**精确地画回图纸视图里**——管线的骨架就通了。

### 第 4 步：标注第一批（下一步）

到这一步才需要数据：先用 §6.1 的自举脚本从 DXF 生成合成集，再人工标 50 张真实 PDF。
有了数据，`model.train(dataset_dir=…)` 就能跑第一版。

| **M5 产品化** | 部署形态定档、设置项、模型分发、MCP 读工具 `tamias_detect_symbols` | 2 |

**合计约 13 人日 + 30~40 人时标注。** 不含训练算力与调参的反复。

M2 的起点命令（RF-DETR 要求 COCO 格式，目录结构
`<dataset>/{train,valid,test}/_annotations.coco.json`）：

```python
from rfdetr import RFDETRSmall

model = RFDETRSmall()
model.train(
    dataset_dir="datasets/arch-symbols",
    epochs=50,
    batch_size=4,
    grad_accum_steps=4,   # 有效 batch = 4×4 = 16，这是官方建议的目标值
    lr=1e-4,
    output_dir="runs/v1",
    early_stopping=True,
)
```

有效 batch 靠 `batch_size × grad_accum_steps` 调到 **≈16**；显存小就降 `batch_size`、
升 `grad_accum_steps`，**乘出来的有效 batch 保持不变**。

### 9.1 M5 附带的便宜胜利：MCP 读工具

`tamias_detect_symbols`（`mutates = false`）返回当前图纸的检出框 + 类别 + 置信度
（**图纸坐标**，不是像素坐标）。这让内置 AI 面板和外部 MCP 客户端能「看见」图纸——
和 [RAG](PLAN-RAG.md) 的 `tamias_search_docs` 是同一形状，也是
[AI 接入 B5](DECISION-AI-INTEGRATION.md) 「截图多模态」最便宜的一步。

意义在于：模型现在能说「这张图 3 号轴交 B 轴有一樘 900 的门」，因为它**看得见**，
而不是靠 [§6 的两段式武装](DECISION-AI-INTEGRATION.md) 让用户去点。

## 10. 验收与指标

| 层 | 指标 | 门槛 |
|---|---|---|
| 检测（矢量回投集） | 门窗 mAP@50 | ≥ 0.85 |
| 检测（真实 PDF 集） | 门窗 mAP@50 | ≥ 0.60（跨来源，先低） |
| 端到端 | 复核表中候选**采纳率** | ≥ 0.85 |
| 端到端 | 门窗**漏检率**（对照纯规则基线） | 相对下降 ≥ 50% |
| 性能 | A1 单次检测（含切片） | ≤ 60 s，UI 不冻结 |
| 回归 | `tests/drawing_import_tests.cpp` 金样 | **不变**：不接证据时逐位一致 |

**mAP 是给论文看的，采纳率和漏检率才是给产品看的。** 理由：

- 一个**假阳性**，用户在复核表里取消勾选花 3 秒；
- 一个**假阴性**，用户要手工建那个构件，而且是**他没意识到自己被坑了**的那种；
- 一个**被漏过没取消**的假阳性，产出的是一份脏模型。

→ 所以 **recall 优先于 precision**，并且这两个指标要在**复核对话框里量**（记录用户
勾选/取消的行为），不是在 Python 评测脚本里量。评测脚本只负责 mAP 这一层的回归。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| **没有公开中文图纸标注集** | §6.1 自举 + §6.3 人工 50 张冷启动；分批标注 |
| 自举标注把规则的错误学进去 | 只用置信度 1.0 的类；5% 人工抽检；抽检不过的类退回人工 |
| 合成集与真实 PDF 分布不一致 | 验证集必须分两组、分开报指标 |
| 跨设计院图例差异大（门窗符号、图层命名、图框） | 测试集按来源分组报指标；不报单一汇总数字 |
| 栅格图纸比例标定错误 → 整个模型尺寸错 | 两点定标 + 结果显式确认 + 超阈值警告 |
| 分辨率不足导致小符号消失 | 切片是必需品（§7.1）；M0 就把切片做进去 |
| 长推理冻结界面 | 后台线程 + 进度 + 取消（§7.6） |
| RF-DETR 的 ONNX 后处理写错（静默出错） | §7.5 四条；导出后用已知图对一遍再往下走 |
| 误用 XL / 2XLarge 权重 | 那两个是 **PML 1.0**，不是 Apache-2.0；**只用 Nano / Small / Medium / Large 和全系 Seg** |
| **期待管理**：有人以为检测器能自动出完整 BIM | §1 写在最前面；默认关闭；候选表是唯一的出口 |

## 12. 与现有纪律的偏离（必须点名）

本方案是仓库里**第一个引入运行时第三方依赖**的特性：

- S1 sidecar → 运行时依赖 Python 解释器；
- S2 ONNX Runtime → 运行时依赖一个原生推理库。

[RAG 的纪律](PLAN-RAG.md)是「零新增第三方依赖、Python 只做构建期离线」，
[MCP](DECISION-AI-INTEGRATION.md) 是「纯 C++、零第三方 JSON」——**视觉做不到**，
因为模型必须在**运行时**对**用户的图**跑，没有构建期可言。

所以「默认关闭 + 编译开关 + `src/vision/` 不进内核依赖树」是硬要求，不是偏好：
默认构建里，Tamias 和今天**逐字节一样**。
